SAP MCP Connection Manager

Manage your SAP connections and MCP clients.

Before your first connection

You need all three of the following:

  • An accessible SAP account, correct SAP client number and permission to use the required ADT services.
  • A reachable SAP HTTPS address, including VPN access and a trusted CA certificate if your company requires one.
  • A supported installed MCP client: Claude Desktop or Codex. A ChatGPT browser session alone is not enough for this local connector.

Installation does not confirm your SAP credentials or permissions.

New connection

Find your SAP HTTPS address
  1. In SAP GUI, enter transaction SMICM, then choose Goto → Services.
  2. Find the active HTTPS service and note its host name and port. Ask your SAP Basis administrator if you cannot access this screen.
  3. Enter https://host:port, for example https://sap.example.com:44300. Enter the SAP client separately.

If your company uses SAP Web Dispatcher or a reverse proxy, ask Basis for the externally reachable ADT address. The internal SMICM address may not work from your PC. Do not use a SAP GUI message-server address or a Fiori page URL.

SSO uses the MCP server’s browser authentication. Testing may open your SAP sign-in page.

Most connections need nothing here. Choose a certificate only when your SAP server’s CA is not already trusted by this computer — your SAP administrator supplies it, and a copy is kept with your Bridge data.

Setup Guide

Follow these steps in order. You can return here at any time without losing the connection form.

1. Check your SAP account and permissions

Confirm your username, password or supported SSO method, and three-digit SAP client number with SAP Basis. Your account must be valid, unlocked and authorized for the required ADT services and operations. SAP GUI access alone does not prove ADT access. Ask Basis to enable the required services and assign only the permissions you need.

2. Find a reachable HTTPS address

  1. In SAP GUI, enter SMICM, then choose Goto → Services.
  2. Find the active HTTPS service and its host and port. Enter https://host:port in SAP system URL; enter the SAP client separately.
  3. If your company uses Web Dispatcher or a reverse proxy, ask Basis for the reachable ADT endpoint instead of assuming the internal host works.
  4. Connect to the required VPN. Check that the address is reachable from this computer. A Fiori page, SAP GUI message server or SAP Logon entry is not necessarily the ADT address.

3. Set up TLS trust

Leave the certificate field empty if the runtime already trusts the server's CA. Otherwise, obtain the issuing CA certificate or chain from Basis.

  1. Open the exact SAP HTTPS address in a browser.
  2. Open the site-information icon beside the address (sliders, padlock or shield), then connection/certificate details.
  3. Inspect the certification path. Export the Basis-approved CA certificate as Base64 X.509 / PEM, with .pem, .crt or .cer extension. The Bridge accepts PEM and DER X.509 certificates, and PEM certificate bundles.
  4. Alternatively, Basis can use STRUST → SSL server Standard or the server PSE used by the endpoint, select the appropriate certificate and export Base64. A proxy can have a different certificate.
  5. Use Choose certificate; Bridge stores a managed copy. Do not upload private keys. Do not trust an unexpected certificate warning without checking with Basis.

The leaf/server certificate alone is usually insufficient unless it is self-signed and confirmed by Basis. Keep TLS verification enabled. Leave TLS server name blank unless Basis supplies an approved hostname override. This certificate is unrelated to Windows app signing.

4. Install and configure your MCP client

  1. Install and open Claude Desktop or Codex, completing its own sign-in/setup.
  2. Create your connection in Bridge, set its authentication and policy, then save it.
  3. Click Configure MCP clients. Read the per-client notification and open Logs for details. Missing clients are skipped; install one and retry if needed.
  4. The managed connector is named SAP-Bridge. Configuration changes are backed up. Supported older local SAP registrations are migrated; unrelated/custom connectors are preserved or reported for manual attention.
  5. Fully quit and reopen the client, then check that SAP-Bridge is enabled. Ask it to list systems and run a system profile check.

ChatGPT/Codex label: the OpenAI integration here writes the local Codex config.toml. It does not configure a ChatGPT website connector or a separate remote ChatGPT service. Client detection does not guarantee that every installed ChatGPT application supports this configuration.

After connection or policy changes, restart clients again. Existing running MCP servers do not automatically reload saved settings.

5. Test the complete connection

Select a saved connection and use Test through MCP. Then run Full diagnostics to check the Bridge and configured launchers. Review Logs. A successful test covers the tested operations, not every SAP function or permission. Finally check SAP-Bridge from the actual client you intend to use.

Safety policy limitations

These controls are additional safeguards, not guaranteed isolation. The bundled MCP server checks every policy itself, before a request reaches SAP and independently of what a client approves. A prompt saying “ignore the policy” does not disable those checks. What each control does:

  • Safety level: three levels, about one question — what may be changed. 1. Read only: nothing can be changed. 2. Custom writable: changes are confined to the customer namespace, judged by the package an object belongs to (Z*, Y*, $* and /namespace/ packages); standard objects stay readable but cannot be changed, including by running a standard class. Choosing it also adds toolset:debugger, toolset:git, runSnippet and runClass to Denied tools, where they can be removed. 3. Standard writable: changes are allowed anywhere this SAP account is authorised.
  • The rating is read from the whole policy, not the level alone. It appears for a few seconds whenever something changes. Narrowing a list lowers it; leaving one open raises it. An allowed-packages list of only Z* confines changes to the customer namespace whatever was picked, so the selection moves to the middle option and the form explains why. A list containing only * matches everything and is called out as restricting nothing.
  • What data may it read: asked separately from the change level, because it governs reading data rather than changing objects. Tables only lets it open a table you name and refuses SQL it composes itself; tables and its own SQL queries allows both. Naming a table outright also means the table lists match it exactly, where a query has to be read out of its text.
  • Allowed packages: changes only inside the listed packages. This limits changes, not reads.
  • Allowed / denied tables: applies to table reads and to SQL, including quoted identifiers such as FROM "USR02". A denial always wins over an allowance.
  • Allowed / denied tools: tool names, wildcards such as transport*, or toolset:name for a whole group. Sign-in and health tools stay available so the connection can still be opened and diagnosed. A denial always wins over an allowance.
  • Allowed transports: changes only under the listed transports, and creating new ones is refused.

Every gate above is exercised against the bundled MCP server itself before each release, both for what it must block and for what it must still allow. What they still cannot do:

  • Reads are not limited by package. Anything the SAP account can see can be read, including standard source.
  • The package gates decide on the package of a target object, so tools that act on something else are not weighed against them. Choosing the middle level denies the debugger and abapGit for you. Transport control (release, delete, set owner) and ATC exemptions stay available whatever namespace they touch, because custom changes in a transportable package need transports; deny toolset:transports or toolset:atc to close them. Code the AI writes and then runs, through runSnippet, runClass or unit tests, acts with your SAP account’s own authorisations, so no namespace limit can bound what it does. The middle level denies runSnippet and runClass, and leaves unit tests available because they are how the AI checks its own work; deny unitTestRun to close that too. The form names whichever of these groups are still open, next to the policy.
  • A write tool whose target cannot be determined from its arguments is refused on a closed package policy rather than allowed through.
  • Deciding the package of an existing object requires asking SAP, so those checks depend on the connection working. Where the package cannot be determined, the request is refused rather than allowed.
  • An activation batch above 200 objects is refused rather than partly checked.
  • Table names are read from the text of a request. SQL assembled at runtime inside ABAP source may not be recognised; the "tables only" reading choice closes that path.
  • They cannot protect against a second, unrestricted connection, or against an agent with filesystem or terminal access that can edit the configuration or start a different server.

Whether a request succeeds also depends on SAP syntax and permissions, and clients must be restarted to load a changed policy. SAP-side authorisations remain the underlying restriction: these controls narrow what an MCP client will attempt, they do not replace what SAP itself permits.

Backups, import and deletion

Use Encrypted connection backup to export settings, credentials and certificates with a passphrase of at least 12 characters. The file is locked by that passphrase and nothing else, so anyone holding both the file and the passphrase can restore your connections, and the SAP passwords in them, on any computer. Treat the passphrase as being as sensitive as the passwords themselves, send it by a different route from the file, and keep your own copy safe — it cannot be recovered. Before import, enter the passphrase used for that backup. Import adds missing connections and preserves existing ones. Imported records are held to the same rules as the connection form, and a record that fails cancels the whole import. Knowing a backup’s passphrase only shows who produced the file, not that its contents are safe, so treat a backup from somebody else as you would any other file they sent you: after importing one, check Logs for connections that run an external program on connect or that have certificate verification disabled. “Import existing connections” skips previously removed destinations so an old configuration cannot silently restore them. To restore deliberately, use New or an encrypted backup. Clearing Logs does not clear deletion protection or configuration backups.

Troubleshooting

  • 401 / sign-in rejected: check username, password, SAP client, account lock/expiry and authentication method.
  • 403 / forbidden: ask Basis to check ADT and operation permissions; changing a password may not help.
  • Invalid certificate: export a real public X.509 certificate; changing the extension is not conversion.
  • TLS failure: verify the host, certificate expiry, issuing CA chain and proxy with Basis. Do not leave verification disabled.
  • Timeout / host not found: check VPN, DNS, host, port, firewall, SAP availability and pending SSO sign-in.
  • Client setup failed: review Logs for invalid JSON/TOML, write permissions or a conflicting SAP-Bridge name. Preserve backups when repairing configuration.
  • MCP launch failed: verify installation and client settings; review OS security restrictions and reinstall from your trusted distribution if files are missing.
  • Other errors: preserve the relevant Logs entry and ask your support contact. Remove credentials and sensitive SAP data before sharing diagnostics.

About SAP MCP Connection Manager

Bridge keeps your SAP connections in one place and hands them to an MCP client — Claude Desktop or ChatGPT/Codex — so it can work with your SAP system on your behalf. It holds your credentials, your certificates, and the safety limits you set for each connection.

Does Bridge collect anything about me?

No. There is no analytics, no telemetry and no usage reporting in it. It does not phone home, it does not check for updates by itself, and it never uploads your connections, your credentials or your SAP data anywhere.

Does it need an internet connection?

Bridge itself does not. It needs to reach your SAP system, which is usually on your company network or through a VPN. If you chose browser SSO or OAuth it will also contact the sign-in service you configured. A few optional SAP tools can fetch reference material from the internet, but only when you use them. Nothing else reaches out.

Does my SAP data leave this computer?

Yes — once an AI client uses it. That is what the app is for: what SAP returns is passed to Claude or ChatGPT/Codex so it can answer you, and from that point it is handled by that provider under your account and your organisation’s settings. Bridge keeping things locally does not change that. If your SAP data is sensitive, check your organisation’s policy and the client’s privacy settings first. The safety policy on each connection is how you limit what a client can reach in the first place.

Where is my information kept, and can anyone else read it?

That folder holds your connection settings, your certificates and the activity log. Your SAP passwords are not in it. On Windows they are encrypted for your Windows account; on a Mac they are in your Keychain. Someone signed in to this computer under a different account cannot read them.

It is not protection from programs already running as you: using a connection means decrypting its password and handing it to the MCP server.

If I send someone an encrypted backup and tell them the passphrase, can they open it?

Yes. The file is locked by the passphrase and nothing else, so anyone holding both can restore your connections — including the SAP passwords inside them — on any computer. That is deliberate: it is how a backup moves from one machine to another. It also means the passphrase is as sensitive as the passwords themselves. Send the file and the passphrase by different routes, never in the same message, and only to someone who is meant to have your SAP access.

Without the passphrase the file is useless to everyone, including you. It cannot be recovered or reset, so keep it somewhere you will still have it later.

What can an AI client actually do in my SAP system?

Whatever your SAP account is allowed to do, narrowed by the safety policy you set on that connection. A new connection starts read only. The policy is checked by Bridge’s own MCP server before a request ever reaches SAP, so instructing the AI to ignore it has no effect. It is a safeguard rather than a replacement for SAP authorisations — the Setup Guide sets out what it does and does not cover.

Can the AI edit Smartforms, Adobe Forms or SAPscript?

No. These forms are built in SAP GUI (transactions SMARTFORMS, SFP and SE71), and Bridge works through the same development interface as Eclipse, which does not offer them. The AI cannot open, change, check or activate a form. Make form changes yourself in SAP GUI. The AI can still help with the code around a form, such as its print or driver program, and explain what to change in the form.

What happens if I uninstall Bridge?

Your connections, certificates and logs stay in the folder above, and your saved passwords stay in the Windows or macOS credential store. Removing the app leaves both untouched, and nothing in your SAP system is changed by installing or removing Bridge.

Anything else worth knowing?

The window you are looking at talks to a small service running only on this computer, and nothing outside this machine can reach it. Updates are yours to choose and install: download a newer installer and run it, and your connections, passwords and certificates are kept.
